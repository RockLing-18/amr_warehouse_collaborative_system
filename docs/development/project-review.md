## 0. 结论摘要

**这是一个「分布式云边端系统集成 + 协议 / 状态机工程」项目，不是「机器人算法」项目。** 1.9 万行自写代码、150 个源文件、11 张表、四工作空间隔离，工程量真实；架构与协议设计是其强项。

但按"打动面试官"的权重衡量，短板集中在**可证明性**而非功能量：零自动化测试、验收清单里最有含金量的异常链路未验证、README 无法在 30 秒内讲清项目、演示缺少物理交互与可视化。综合评分约 **5.4 / 10**，且这些短板基本都属于呈现层与验证层，**架构不需要推倒重来**。

| 维度 | 得分 | 判断依据 |
|---|---|---|

| 协议与接口设计 | 8.5 | 任务状态机、幂等、ACK、补报、ADR 治理齐全 |
| 工程鲁棒性设计 | 8.0 | 心跳超时、共享状态、生命周期竞态处理、原子落盘 |

| 文档治理一致性 | 4.0 | 23 份文档但状态漂移、版本写错 |
| 机器人算法深度 | 3.0 | Nav2 默认配置，无调度 / 交通 / 电量闭环 |

## 1. 定位与岗位匹配

投 **ROS2 系统工程师 / 机器人软件开发 / 云边端后台 / 上位机**，这个项目很能打；投 **SLAM、运动规划、控制算法**，三句话就会被问穿——代码里几乎没有算法，全是编排。

因此第一句定位应当是「多机器人任务编排与状态同步系统」，而不是「智能仓储 AMR 云边协同仿真平台」。后者会让面试官预期定位、避障、抓取，而这些恰好是 V1 明确不做的。**名字决定预期，预期错了，做对的部分也会被当成缺失。**

## 3. 五个硬伤（文件级证据）

**3.1 零可证明性（最致命）。** 1.9 万行 / 150 个源文件，测试只有 3 个 ROS2 模板 lint（`test_copyright.py` / `test_flake8.py` / `test_pep257.py`），无 gtest、无集成测试、无 CI、无根目录 LICENSE。而 `v1-acceptance-checklist.md` 中 **AC-011 任务取消、AC-012 ~ 014 断网续行与结果补报明确标注「Planned，本轮不测试」**——恰好把含金量最高的异常链路藏在没验证的地方。设计得像工业级，却拿不出一条证据，这是全场最亏的一处。

**3.2 文档自己给自己扣分。** 全仓文档状态词频：`Not Started` 38 / `Planned` 32 / `Partial` 30 /「尚未」19，而 `Implemented` 仅 14；`TODO.md` 写 SRS V0.12 实为 V0.18；`edge_server.md`、`amr-application-design.md`、`edge-data-model.md` 把已实现的 Task Service / 行为状态机 / 11 张表标为 Planned；SRS 内还有 19 个 TBD。**文档多不等于严谨，不一致比没有文档更糟**——它会坐实「用文档冒充工程量」的怀疑。

**3.3 假数据与死代码。**

| 位置 | 问题 |
|---|---|
| `amr_agent_node.cpp:296`、`amr_behavior_manager_node.cpp:562` | `battery = 100.0` 硬编码，但数据库 / 协议 / 状态机都有该字段，等于上报假数据 |
| `amr_communication.cpp:111-114`、`edge_communication.cpp:153-156` | `TRAFFIC_RIGHTS_REQ` 订阅整段注释，`TrafficBridge` 为空壳 |
| `tool/.../warehouse_tool.py:522/542/550/558/583` | 五个 `upload_*` 仍是 `not implemented yet` |
| `amr_simulation.launch.py` | 5 行空实现 |
| `cloud_platform/`、部分 docs 目录 | 仅 `.gitkeep` 占位 |

**3.4 明文凭据。** `edge_server/config/edge_server.yaml:23` 曾硬编码明文 MQTT 密码（具体值已隐去），且经 `bootstrap_service.cpp:31` 下发给 AMR；而 `.gitignore` 已忽略 `*.env`，SRS 又有 NFR-009。**自相矛盾比失误更伤**——面试官会问「你知道该外置，为什么没做」。本轮已按 A 方案修复（见第 9 节）。

**3.5 不可复现。** `setup_simulation.sh` 只有 3 行 `source`，没有依赖安装、编译、启动与健康检查；`build-run.md` 写死绝对路径 `/home/zyr/code/...`。别人 clone 跑不起来，视频里的可信度就只能靠「信我」。

## 4. 一个反直觉判断：文档体系目前是负资产

SRS + 接口契约 + 7 份架构文档 + ADR + TODO + 验收清单，看着像大厂流程，但一个人做的项目摆 23 份文档本身就会触发警惕；再加上状态漂移和版本写错，警惕就变成实锤。

**建议对外只保留四件**：README（30 秒定位 + 3 个技术亮点 + 一键跑 + 30~60s GIF）、一张架构图、一页 ADR 讲 2~3 个关键取舍、一份带日志 / 截图 / DB 前后对比的验证报告。SRS 与契约收进 `docs/` 作为「深挖材料」，不要在首页堆。

> 待确认：SRS 决策 D-002 规定「README 采用 V1 当前范围 + 未来愿景 的结构」。本轮 README 已改为面试导向结构，但**未改动 SRS**（需求基线需授权）。建议后续把 D-002 更新为「README 面向读者分为对外展示与范围声明两部分」，否则基线与实际文件不一致。

## 5. 被埋没的三块真金

**5.1 幂等合并。** `tbl_amr_task_status_event` 幂等表 + `pending_task_reports.json` 原子写 + `status/ack` 清理，解决 at-least-once 语义下的状态收敛与重复上报。这是分布式系统的真问题，能单独讲十分钟，却埋在 `sqlite_db.cpp` 1513 行里。

**5.2 生命周期状态机。** `WAITING_CREATE → LAUNCHING → WAIT_GAZEBO_MODEL → WAIT_CONTROLLER → ACTIVE`，处理「进程起来了但 Gazebo 模型 / controller_manager 未就绪」的竞态。比十个 CRUD 都有说服力。

**5.3 多机隔离。** `robot_id + "_"` TF 前缀（`map` 除外）+ 按 `robot_id` 动态生成 Nav2 参数 + 独立 controller_manager，是 ROS2 多机器人最经典的坑。

**5.4 隐藏资产：51 条已确认决策。** SRS 1.5 节 D-001 ~ D-051 记录了「主动砍了什么、为什么砍」。能讲清取舍比罗列功能更能打动高级面试官，但目前完全没被提炼到对外材料里。本轮 README 已提炼其中 5 条。

## 6. 演示可信度深挖

这一节单独展开，因为**视频是「增加可信度」的载体，而当前设计会让视频反过来削弱可信度**。

### 6.1 当前视频实际能拍到什么

| 镜头 | 画面 | 观感 |
|---|---|---|
| 启动 | 终端刷日志、Gazebo 里出现仓库和两台车 | 正常，但和所有 ROS2 demo 一样 |
| 任务注入 | `curl POST /api/tasks` 回显 JSON | 只有文字，没有画面变化 |
| 执行 | 小车沿 Nav2 路径移动到取货点、停住、再移动到卸货点 | 有运动，但没有交互 |
| 抓取 / 放置 | **什么都没有**，只有数据库字段变化 | 最弱的一环 |
| 完成 | 状态字段变为 COMPLETED | 只有文字 |

### 6.2 六个 SRS 决策如何共同削弱「机器人感」

| 决策 | 内容 | 对演示的影响 |
|---|---|---|
| D-026 | 抓取动作以数据变化代替 | 没有任何物理交互 |
| D-045 | `GRASPING` / `PLACING` 固定延时或状态直接推进 | 停顿看起来像卡顿，不像作业 |
| D-047 | 导航失败不自动重试，直接 `CARRY_ABORTED` | 没有失败恢复镜头 |
| D-032 | V1 不主动使用 `FAILED` | 状态机看起来「过于顺利」，不真实 |
| D-005 | V1 不交付交通路权协调与电量管理 | 两台车各跑各的，谈不上「协同」 |
| D-015 | `robot_ids` 非空，Edge 不自动选 AMR | 没有调度决策可展示 |

叠加效果是：**没有物理交互、没有失败、没有恢复、没有调度、没有多车博弈**。再配上 `battery = 100.0` 这类硬编码，一旦视频里出现状态面板，反而会暴露假数据。面试官看完的典型疑问是：「所以这是一个会动的数据库状态机？」

### 6.3 面试官看视频时的三个追问

1. 「机器人真的搬东西了吗，还是只改了个字段？」→ 指向 D-026 / D-045。
2. 「断网了会怎样，你怎么证明？」→ 指向 AC-012 ~ 014 未验证。
3. 「两台车相遇怎么办？」→ 指向 V1 无交通协调。

这三个问题本身不是扣分项，**答不上来才是**。而目前仓库里没有任何材料能支撑回答。

### 6.4 不造假的前提下提升可信度（按 ROI 排序）

**A · 把「看不见的状态」变成「看得见的证据」（成本最低，收益最高）**

- **断网注入演示**：停掉 EMQX 或断开 AMR 的 MQTT 20~30 秒，终端展示 `pending_task_reports.json` 原子落盘；恢复后展示补报日志与 Edge 侧 `tbl_amr_task_status_event` 行数不变。这一条把最强的设计变成可证明的行为，是视频的高潮。
- **SQLite 前后对比**：`sqlite3 edge.db "select count(*) from tbl_amr_task_status_event"` 在重复上报前后各查一次，证明幂等。
- **只读状态看板**：机器人位置 / `task_state` / `goods_status` 四量实时展示，哪怕先用 `watch` + `jq` 美化终端也可以。让数据变化可见，弥补没有物理交互。

**B · 补一点真实物理交互（成本中等，画面收益最大）**

在 Gazebo 里加一个简单货箱模型，用 attach / detach 表现「货物跟着车走」；或至少在 RViz 用 Marker 显示拾取与放置。**不需要机械臂、不改协议、不改状态机**，只把 D-026 的「数据变化」升级为「模型变化」，就能把「状态机动画」变成「搬运」。

**C · 让多机真的协同一次（V2 最小演示）**

两台车在狭窄通道相遇，一台让行。哪怕用静态路口优先权规则实现，画面感和话题性都远超「两台车各跑各的」，同时直接回应第 3 个追问。

**D · 量化与可复现**

一张 N 机 × M 任务的完成时间 / 成功率 / 冲突次数表；一段真正能跑起来的启动脚本；明确标注「Gazebo 仿真，非真实硬件」。**诚实标注边界反而加分**，面试官最反感的是把仿真说成实物。

### 6.5 建议的 60~90 秒分镜

| 时间 | 画面 | 字幕要点 |
|---|---|---|
| 0 ~ 8s | 架构图 + 一句话定位 | 「不是路径规划，是任务编排与状态同步」 |
| 8 ~ 20s | Gazebo 两台 AMR spawn，RViz 显示各自 namespace / TF 前缀 | 多机隔离 |
| 20 ~ 35s | `POST /api/tasks` → MQTT `task/assign` → 两车同时出发 | 协议分层、区域寻址 |
| 35 ~ 50s | 看板上 `goods/request` 审批、6 态状态机推进、四量变化 | 共享任务池、分趟搬运 |
| 50 ~ 68s | **停 broker 20s → 待补报落盘 → 恢复 → 补报 → 幂等表行数不变** | 断网续行与幂等合并（高潮） |
| 68 ~ 80s | 任务完成、SQLite 查询、验收清单勾选状态 | 结果可验证 |
| 80 ~ 90s | 一页「设计取舍 + 已知边界」 | 诚实收尾 |

### 6.6 红线

- 不要剪掉异常 / 失败镜头后声称「从未失败」；
- 不要把固定延时说成「机械臂抓取」；
- 不要用加速播放掩盖等待；
- 不要在 README 写「已实现交通管理 / 电量管理」；
- 不要在画面里出现含明文密码的配置文件（本轮已修）。

## 8. 对 V2 优先级的逆耳建议

按 ROI，**V2 最不该先做的是 Cloud Platform**：按 ADR-0001 它只是把 HTTP 换成 MQTT，功能增量小、面试话题增量更小，且 SRS 里 19 个 TBD 说明上游形态尚未冻结。

建议顺序：

1. **交通路权协调（V2）** —— 唯一能把「算法深度」从 3 分拉到 7 分的东西。路口优先权、冲突消解、死锁避免，可复用已被注释的 `TRAFFIC_RIGHTS_REQ` topic；同时补上「两车互相让行」这个最有画面感的镜头。
   > **2026-11-20 第七轮更新**：该能力已定案为 `amr_behavior_manager` 包内 `TrafficGate`，**不设独立模块**；topic 已定名为 `traffic_request` / `traffic_response`（ROS2）与 `amr/{robot_id}/traffic_rights/request` / `response`（MQTT）。详见 `docs/architecture/roadmap/v2-implementation-spec.md`。
2. **只读 Web 看板** —— 成本低于 Cloud Platform，但直接改善演示与可证明性。
3. **Cloud Platform** —— 最后做，保留 V1 的 HTTP 注入接口作为兼容入口。
