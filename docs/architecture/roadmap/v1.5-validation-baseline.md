# V1.5 验证基线 · 开发任务书

**Status:** Planned
**所属路线图:** [`../version-roadmap.md`](../version-roadmap.md)
**版本主题:** 不新增业务功能，只补齐 V1 的测试证据与可观测性
**前置依赖:** V1 已交付（见 `docs/development/v1-acceptance-checklist.md` AC-001~010、015~018）

---

## 1. 目标

把 V1 中「代码已实现但从未验证」的异常链路真正跑一遍，形成可复现、可归档、可直接用于面试沟通的证据；同时建立后续每个版本都能复用的验证设施。

> **为什么必须先做**：SRS 10.3 节「V1 完成定义」规定「达到条件后，应先整理项目成果、测试证据和文档，再决定是否启动 V2」，而取消、断网续行、结果补报三项都在完成条件内，验收清单里却标注「Planned —— 本轮不测试」。V2 会引入更多异常路径，若此时没有故障注入与取证能力，后续每一版都只能靠手工演示。

## 3. 功能细节

### 3.1 AC-011 ~ AC-014 实测与取证

#### 3.1.1 AC-011 任务取消

复现命令（沿用验收清单）：

```bash
curl -X POST http://127.0.0.1:8080/api/tasks/task_v1_unload_10/cancel
```

必须验证三个子项：

| 子项 | 预期 | 取证位置 |
| --- | --- | --- |
| 任务进入 `CANCELLED` | `GET /api/tasks/{id}` 返回 `state=CANCELLED`；`tbl_task.state` 一致 | HTTP 响应 JSON；`sqlite3 /opt/amr/data/edge.db "SELECT task_id,state FROM tbl_task WHERE task_id='task_v1_unload_10';"` |
| AMR 取消当前导航、在途申请回退 `in_progress` | `task_state` 变为 `CANCELLED`；`tbl_task_goods_allocation` 中该 `request_id` 的 `state` 变为 `ABORTED`；四量恢复 `pending` | `amr_behavior_manager` 日志（`TASK_CANCELLED`）；`sqlite3 ... "SELECT request_id,state,quantity FROM tbl_task_goods_allocation WHERE task_id='...';"`；`SELECT goods_id,total_quantity,in_progress_quantity,completed_quantity,pending_quantity FROM tbl_task_goods_status WHERE task_id='...';"` |
| 不覆盖已完成终态 | 对 `state=SUCCEEDED` 的任务再发 cancel，状态保持不变并返回明确错误 | HTTP 响应；`tbl_task_event` 不应新增 `CANCELLED` 事件 |

同时验证四量不变式（INV-07）：

```sql
SELECT goods_id,
       total_quantity,
       in_progress_quantity + completed_quantity + pending_quantity AS sum_qty
FROM tbl_task_goods_status WHERE task_id='task_v1_unload_10';
-- 要求 total_quantity = sum_qty 且 in_progress_quantity = 0
```

> 关联 TBD：TBD-004（取消时的安全停止策略）、TBD-009（断网期间的取消）、TBD-012（终态任务是否允许重新下发）。本版本只需给出**最低可行规则并记录**，不要求修改代码。

#### 3.1.2 AC-012 断网续行

两个独立断网场景，必须分别测：

| 场景 | 操作 | 预期行为 | 证据 |
| --- | --- | --- | --- |
| A：Edge Server 进程停止 | `kill` Edge 进程，保持 EMQX 运行 | AMR 完成**当前已获批**的那一趟搬运，之后停止下一趟货物申请；不卡死、不乱跑 | `amr_agent` 日志中的 `edge online=false`；`amr_behavior_manager` 中 `maybeRequestNextGoods()` 因 `m_edge_online=false` 提前 return 的日志 |
| B：Edge 侧 EMQX 停止 | 停止 broker，Edge 仍在 | AMR 检测 MQTT 断连并停止后续申请 | `edge_communication.cpp` 的 `setConnectionLostCallback` 日志；`pending_task_reports.json` 开始增长 |

关键取证时间点（建议按秒记录，形成时间线表）：

```text
T0   正常执行中，记录 tbl_task_goods_status 快照
T1   注入断网
T2   当前趟完成，记录 CARRY_COMPLETED 生成
T3   确认无新的 goods/request 发出
T4   恢复网络
T5   补报重传、收到 ACK
T6   记录最终 DB 快照
```

#### 3.1.3 AC-013 结果补报

- 断网期间产生的 `CARRY_COMPLETED` 必须写入 `/opt/amr/data/amr_runtime/pending_task_reports.json`，格式遵循 `docs/requirements/pending-task-reports-format.md`。
- 验证**原子写入**：检查 `.tmp` 文件出现与 `rename` 完成之间不存在半写入状态（`pending_report_store.cpp::save()` 已实现 `.tmp` + `fs::rename`）。
- 恢复后自动重传，收到 `amr/{robot_id}/task/status/ack` 后按 `acked_message_ids` 清理本地记录。

```bash
# 断网中
cat /opt/amr/data/amr_runtime/pending_task_reports.json
# 恢复后（应清空 reports 数组）
cat /opt/amr/data/amr_runtime/pending_task_reports.json
```

#### 3.1.4 AC-014 幂等

- 手工重放同一条 `CARRY_COMPLETED`（相同 `message_id`）两次，验证 `tbl_amr_task_status_event` 行数**不增加**、货物 `completed_quantity` **不重复累加**。
- 验证终态不被覆盖：对 `SUCCEEDED` 任务重放旧 `STATUS`，任务状态不变。

```sql
SELECT COUNT(*) FROM tbl_amr_task_status_event WHERE task_id='...';
SELECT message_id,event_type,received_at FROM tbl_amr_task_status_event WHERE task_id='...' ORDER BY received_at;
-- 依据 INV-08：UNIQUE(message_id, task_id, robot_id, event_type)
```

> 关联 TBD-010（Edge 最后已知状态与 AMR 补报不一致时的合并规则）。本版本需记录实际观察到的行为。

### 3.2 故障注入框架（新增验证设施）

**建议落地形态**：独立脚本目录 `tool/fault_injection/`（Python + shell），**不进入 ROS2 包、不改业务代码**。

必须支持的注入点（每个注入点绑定预期断言）：

| 注入点 | 手段 | 预期断言 | 关联验收 |
| --- | --- | --- | --- |
| Edge 进程停止/恢复 | `kill` / 重启 `edge_server` | 当前趟完成、下一趟停止、恢复后补报 | AC-012 / AC-013 |
| Edge 侧 EMQX 停止/恢复 | 停 broker | 断连回调触发、待补报落盘 | AC-012 |
| MQTT 消息重复 | 重放同一 `message_id` 的消息 | 幂等表行数不变 | AC-014 |
| MQTT 消息乱序 / 延迟 | 延迟投递旧 `STATUS` | 终态不被覆盖 | AC-014 / TBD-010 |
| AMR 进程崩溃重启 | `kill` 单个 AMR 进程并重新拉起 | 本地待补报不丢失 | AC-013 |
| 任务取消 | `POST /api/tasks/{id}/cancel` | 导航取消、配额回退 | AC-011 |
| 地图版本错配 | 注册响应中改 `map_version` | 走地图下载分支且不中断既有任务 | 回归项 |
| `/clock` 时间跳变 | 建议仅记录，见下方说明 | 观察 TF 时间戳告警是否复现 | `nav2-tuning-notes.md` 第 4 节遗留风险 |

**取证脚本要求**：

- 每个场景一条命令可复现，输出统一到 `evidence/<scene_id>/`。
- 自动抓取三类证据：① 相关进程日志片段；② `pending_task_reports.json` 前后内容；③ SQLite 关键表前后行数与四量快照。
- 输出机器可读的 `result.json`（`scene_id`、`pass/fail`、`assertions[]`、时间戳）。
- 失败时保留完整现场，不自动清理。

> `/clock` 跳变属于仿真时间同步问题，侵入性较高，本版本**只要求记录观察结果**，不要求实现注入；是否纳入自动化见 TBD-034。

### 3.3 全链路 `trace_id`（建议零侵入方案）

**目标**：一个 `task_id` 从 `POST /api/tasks` → MQTT 下发 → ROS2 `task_command` / `task_event` → SQLite → `status/ack`，能用一条命令导出完整时间线，用于回答「跨 4 个进程的问题怎么定位」。

**推荐方案（零侵入）**：不改任何 MQTT/ROS2 消息结构，仅在**日志行**中统一附加 `trace_id`，取值复用已有 `task_id`（必要时拼接 `message_id`）。实现为日志格式规整 + 一个聚合脚本 `tool/fault_injection/collect_trace.py`，按 `trace_id` 从各进程日志中抽取并排序输出时间线。

**不推荐方案（需确认）**：把 `trace_id` 写入 MQTT 消息字段——这属于消息字段变更，按 AGENTS.md 需同步 `interface-contract.md` 并事先征得同意，见 **TBD-025**。

### 3.4 一键基准实验

新增 `tool/benchmark/run_benchmark.sh`，固定随机种子与地图版本，执行 N 台 AMR × M 个任务矩阵，自动输出表格：

| 指标 | 数据来源 |
| --- | --- |
| 任务完成时间 | `tbl_task_event` 首末时间戳 |
| 成功率 | `tbl_task.state` 分布 |
| 重复消息数 | `tbl_amr_task_status_event` 中 `sqlite3_changes` 为 0 的插入次数（需日志配合） |
| 断网恢复时长 | 故障注入时间线 T1→T5 |
| 四量不变式违例数 | `CHECK` 约束 + 查询校验 |

输出为 Markdown 表 + CSV，直接可贴进验证报告。**指标定义必须写在脚本头部注释里**，避免后续口径漂移。

## 8. 为什么这么实现（取舍）

- **不新增功能，只补证据**：本项目用于面试，含金量瓶颈不在功能数量，而在「异常处理有没有被验证过」。V1 最硬的幂等合并与待补报机制全埋在代码里，补一次实测的收益高于再加一个模块。
- **故障注入做成脚本而不是改业务代码**：避免为了测试污染已验证链路；脚本可复现、可归档、后续每个版本都能复用。
- **`trace_id` 优先零侵入**：加消息字段属于破坏性变更，需同步契约并确认；仅规整日志即可达到「跨进程定位」的讲述目的，成本更低。
- **文档校准限定在状态词层面**：`srs.md` 是需求基线，本轮不动；只修正与代码不符的状态标注，避免把「文档整理」变成「需求改写」。
